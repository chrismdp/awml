# Drawing the workflows you already run

A person who builds AI routines one at a time ends up with scheduled tasks, bots, saved prompts and automations. This guide turns them into AWML files, one workflow at a time.

The drawing shows what the person's written design and rules say should happen. The runs you trace show what did happen. Where a run did something the design doesn't allow, its line is drawn red. Where two written rules disagree, such as the person's design and an agent's own notes, draw the stricter one and ask the person which they meant.

Draw one workflow at a time with the person, or a few that hand work to each other, each in its own conversation. Ask that workflow's questions while its trace is fresh, rather than collecting them across many workflows into one long list. Steps 1 and 2 can cover everything at once; steps 3 to 11 go one workflow at a time.

Before step 5, read the [spec](SPEC.md) and the [example](examples) nearest your workflow. Steps 5 to 9 use their words.

1. **List everything that runs.** Every scheduled task, cron job, bot, Cowork or Codex task and automation. Include work that starts when something arrives, such as a message, a forwarded email or a hand-off from another task, and any schedule kept inside a note. Read the places they live, not your memory: the live list of scheduled tasks, the automation tool's dashboard, the scripts each one calls, and every script that starts it. Write one line per job: what starts it, how often it ran last month, what it leaves behind, which model and company it uses, with any fallback, and where its records are. Give every time on one clock, read from the scheduler's own settings. List what's switched off, and anything the notes describe that nothing runs: both are findings.

2. **Group the list into workflows.** A workflow runs from one or more triggers to what it leaves behind. A hand-off a task receives is one of its triggers. A task belongs to another's workflow when it runs on an item that task handed it, through a file or a message. A note that many tasks read and write doesn't join them: it's a context in each workflow that uses it. Stop at a hand-off to an agent that also takes work from elsewhere: that hand-off is the workflow's last line. One task doing two jobs that share no steps is two workflows.

3. **Pick the one where the most leaves.** Start with the workflow that sends content to a company or a person outside its scope, or changes something outside: a send, a payment, a booking, an entry in the books or a publication. Posting in the person's own chat is delivery, and content sent to a model the scope allows stays inside it, so neither counts. Count only what happens before the workflow's last hand-off. If several qualify, pick the one where something that can't be undone happens with nobody there, then the one that runs most often.

4. **Trace real runs.** Take a recent run that took the longest path, and follow it end to end in its records: what started it, each piece of work in order, what each read and wrote, what each model was given, and what left the system. A model's input is in its session transcript or request log. An agent's own notes about a run are its account, so check them against the transcript. For each trigger or step the run skipped, trace a short run of it, up to where it joins this one. Follow each hand-off to the first thing that received it, note what that read, then stop. Write the run as a numbered list on one clock, citing the record for each line. Where records disagree with notes or memory, the records win. Where a record is lost, work the line out from the code and what the run left, and mark it inferred. For anything a run did that you didn't expect, find the instruction that asked for it. A step with no record, or an action with no instruction, is a finding.

5. **Mark who decides each step.** Code if it gives the same output for the same input every time, AI if a model makes a judgement, a person if someone has to be there. Mark each step as it runs today, even where code could do it. A step that mixes two deciders is two steps: split a script where it calls a model, and a check inside a script that can refuse becomes a code step of its own. Then give each step one operation: bring in, sort, learn, prepare, check, reflect, draft, do, answer, or other for work that fits none of those. Split any step that would break an operation's rule: only a do step leads to an outside action, and a check or answer step never writes to a context, such as a note.

6. **Name what each step touches.** Its contexts are the notes, rules and state it reads and writes, including any draft, and any log or model session that later steps read back. Its connectors are the outside services it reaches, the open web included: for each, say whose access it uses and what that access could reach beyond this workflow. Its surfaces are where people see its results. Its outside actions are what it changes in the world, each with its tier from the spec and any standing approval named on it. A company that only processes content, such as a model's maker or a page renderer, isn't a connector: it belongs in step 7 and on the platform view. A hand-off to another agent ends at that agent's first step, in that agent's scope.

7. **Say who may see each thing, and find the publishing.** For each context, connector and surface, list the people who may see it and the companies that may process it. Take them from the person's written design, and ask the person where it's silent. Where nobody has said, write "not checked" and keep it as a question. People who see the same things under the same terms form a scope. One scope sits inside another only if all its people are in the other and its terms are at least as strict. A step reads only from its own scope or a wider one. A read from a narrower one is refused, and drawn red if the live system does it. Then mark every hand-off that shows content to more people or under looser terms: that's publishing. So is content sent to a company its scope doesn't allow, and an ID, a path or a link that lets the receiver read the rest. For each one, say what allows it: a person's yes to that item, a standing rule and whose it is, or nothing.

8. **Write the security view and check it.** Write one part per thing, and one line per read, write, start and hand-off, in the order the work flows. Draw each red line from the trace now, labelled with what happened and when. Mark each gap, and each clash between written rules, with a comment. Run `awml check` and fix every mistake until it says `ok`. It reports any `data` line that leaves its box, unless the line is red. It can't tell whether a box is in the right place, so check by hand that each box sits where its people and terms put it. Then check that every line of the trace has a part.

9. **Write the platform view and check it.** Copy the file, change `view` to `platform`, and replace the scopes with platforms. Put each part in the block of the platform it runs on or lives in: an AI step on the machine whose harness calls the model, a connector with the service it reaches, and a person's own step or review on the device they use. Label each block with the model and company it uses, any fallback, and when the machine is on, if that isn't always. Add a comment for anything a machine holds that the drawing can't show, such as the keys a step can read, and whether it has a shell or the open web. Check it, then check that both views have the same parts and lines, apart from comments and any part the platform view leaves out, such as a trigger.

10. **Read the drawing for findings.** Ask these of the drawing and the trace:
    1. What does each red line show the live system doing, and which instruction asked for it?
    2. Does every publishing line have a person's yes or a standing rule? Does anything reach the public without a person's yes to that item? Did the people whose words move agree?
    3. Is each yes given to the exact content, and recorded where the next step can check it?
    4. Does every Ask action have a review in front of it, a person's own `do` step, or a standing approval named on it, with limits, whose actions are listed for that person with how to undo them?
    5. Is each Allow action really Allow? One that can't be undone, is seen outside its scope or spends past a limit is Ask.
    6. Which step takes in text from strangers, and what can it reach?
    7. If a step fails halfway, what has already changed outside, and does a later run notice?
    8. Could any AI step be code? Look at a few weeks of its records: does it give the same answer to the same kind of input?
    9. Is any surface, note or prompt left with nothing keeping it current, any context that nothing writes or nothing reads, or any step that nothing starts?
    10. Does any work that must outlive a person rest on that person's connector?
    11. Does any machine hold something that a company processing content there may not see?
    12. Does every step leave a record that survives a restart, on one clock?

11. **Act on each finding.** Take each finding, with its evidence, to the person who answers for the workflow. They decide whether to change the live system. Until it changes, the drawing keeps the finding: a red line for something the live system did, a comment for a gap. When a fix lands, take the red line away.

Then go back to step 3 for the next workflow.
