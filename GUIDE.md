# Drawing the workflows you already run

A person who builds AI routines one at a time ends up with scheduled tasks, bots, saved prompts and automations. This guide turns them into AWML files, one workflow at a time.

The drawing shows what the person's written design and rules say should happen. The runs you trace show what did happen. Where a run did something the design doesn't allow, its line is drawn red, which `awml check` works out. Where two written rules disagree, such as the person's design and an agent's own notes, draw the stricter one and ask the person which they meant.

Draw one workflow at a time with the person, or a few that hand work to each other, each in its own conversation. Ask that workflow's questions while its trace is fresh, rather than collecting them across many workflows into one long list. Steps 1 and 2 can cover everything at once; steps 3 to 11 go one workflow at a time.

Before step 5, read the [spec](SPEC.md) and the [example](examples) nearest your workflow. Steps 5 to 9 use their words.

1. **List everything that runs.** Every scheduled task, cron job, bot, Cowork or Codex task and automation. Include work that starts when something arrives, such as a message, a forwarded email or a hand-off from another task, and any schedule kept inside a note. Read the places they live, not your memory: the live list of scheduled tasks, the automation tool's dashboard, the scripts each one calls, and every script that starts it. Write one line per job: what starts it, how often it ran last month, what it leaves behind, which model and company it uses, with any fallback, and where its records are. Give every time on one clock, read from the scheduler's own settings. List what's switched off, and anything the notes describe that nothing runs: both are findings.

2. **Group the list into workflows.** A workflow runs from one or more triggers to what it leaves behind. A hand-off a task receives is one of its triggers. A task belongs to another's workflow when it runs on an item that task handed it, through a file or a message. A note that many tasks read and write doesn't join them: it's a context in each workflow that uses it. Stop at a hand-off to an agent that also takes work from elsewhere: that hand-off is the workflow's last line. One task doing two jobs that share no steps is two workflows.

3. **Pick the one where the most leaves.** Start with the workflow that sends content to a company or a person outside its scope, or changes something outside: a send, a payment, a booking, an entry in the books or a publication. Posting in the person's own chat is delivery, and content sent to a model the scope allows stays inside it, so neither counts. Count only what happens before the workflow's last hand-off. If several qualify, pick the one where something that can't be undone happens with nobody there, then the one that runs most often.

4. **Trace real runs.** Take a recent run that took the longest path, and follow it end to end in its records: what started it, each piece of work in order, what each read and wrote, what each model was given, and what left the system. A model's input is in its session transcript or request log. An agent's own notes about a run are its account, so check them against the transcript. For each trigger or step the run skipped, trace a short run of it, up to where it joins this one. Follow each hand-off to the first thing that received it, note what that read, then stop. Write the run as a numbered list on one clock, citing the record for each line. Where records disagree with notes or memory, the records win. Where a record is lost, work the line out from the code and what the run left, and mark it inferred. For anything a run did that you didn't expect, find the instruction that asked for it. A step with no record, or an action with no instruction, is a finding.

5. **Mark who decides each step.** Code if it gives the same output for the same input every time, AI if a model makes a judgement, a person if someone has to be there. Mark each step as it runs today, even where code could do it, with one exception: a fixed procedure that an agent carries out by following instructions, as a scheduled session does with its prompt, is a code step when the design gives it to code. The platform it runs on then says that an agent carries out its steps, and `awml fit` reports each one. A step that mixes two deciders is two steps: split a script where it calls a model, and a check inside a script that can refuse becomes a code step of its own. Then give each step one operation: bring in, sort, learn, prepare, check, reflect, draft, do, answer, or other for work that fits none of those. Split any step that would break an operation's rule: only a do step leads to an outside action, and a check or answer step never writes to a context, such as a note. Any verdict a later run reads is written by a step after the check. Make each `do` step code that acts on an earlier score or choice, and split it so it changes one outside action, surface or set of contexts.

6. **Name what each step touches.** Its contexts are the notes, rules and state it reads and writes, including any draft the workflow keeps for itself, and any log or model session that later steps read back. Its connectors are the outside services it reaches, the open web included: for each, say whose access it uses and what that access could reach beyond this workflow. Its surfaces are where people see its results. Its outside actions are what it changes in the world, including a draft it leaves in an outside service for a person to pick up, each with its tier from the spec and any standing approval named on it. A company that only processes content, such as a model's maker or a page renderer, isn't a connector: it belongs in step 7 and on the platform view. A hand-off to another agent ends at that agent's first step, in that agent's scope. Mark each trigger, connector or context that takes in text anyone can write, such as a web form, a public inbox or the open web, with `untrusted: true`.

7. **Say who may see each thing, and find the publishing.** For each context, connector and surface, list the people who may see it and the companies that may process it. Take them from the person's written design, and ask the person where it's silent. Where nobody has said, write "not checked" and keep it as a question. People who see the same things under the same terms form a scope. One scope sits inside another only if all its people are in the other and its terms are at least as strict. A step reads only from its own scope or a wider one. A read from a narrower one is refused, and drawn red if the live system does it. Then mark every hand-off that shows content to more people or under looser terms: that's publishing. So is content sent to a company its scope doesn't allow, and an ID, a path or a link that lets the receiver read the rest. For each one, say what allows it: a person's yes to that item, a standing rule, whose it is and whose words it moves, or nothing. A standing rule moves only the words of people who agreed to that target.

8. **Write the design and check it.** Start one 0.6 file with its title and scopes. Write one part per thing, and one line per read, write, start and hand-off, in the order the work flows. Each line follows the data, so a read comes out of a connector, and a write or an outside action carried out through it goes in. A run of code steps whose rules tests already hold may be drawn as one code step, if none of them leads to an outside action or reads from another scope, and no AI or person step comes between them. Label it with what the run does and where its tests are, give it the operation its steps share, or `other`, and draw it in full only when a finding sits inside it. Draw each line from the trace that the design doesn't allow as the run took it, labelled with what happened and when. Where a person approved a task once, draw their standing approval as a part between the `do` step and the action, labelled with whose it is and its kinds and limits, with a line to the surface where its actions are listed. Mark a code step `cleans: true` only where its code passes on just what's safe from untrusted text, and say how in its label. Mark each gap, and each clash between written rules, with a comment. Run `awml check` and fix every mistake but those lines. It reports any `data` line that leaves its box and any Ask action with no person in front of it, and it warns of each outside action that untrusted text reaches. Each line it reports that the run really took stays, and `awml draw` draws it red with what's wrong. Describe a breach the check can't find in a comment tied to the part it's about. It can't tell whether a box is in the right place, so check by hand that each box sits where its people and terms put it. Then check that every line of the trace has a part, which for a line inside a run drawn as one step is that step.

   For example, a step that passes on only the mail from a bakery's flour supplier is a fair `cleans` only if its rule for "mail from the supplier" holds. Neither SPF nor DKIM passing is enough alone, because neither checks the From line a reader sees. The rule is DMARC passing for the supplier's domain, which means SPF or DKIM passed for the domain in the From line. Even then, the supplier's mail can quote or forward a stranger's text. So the step is a fair `cleans` only where the supplier's mail can be taken as the supplier's own words. Otherwise it should also strip quoted and forwarded text.

9. **Add an implementation for where it runs.** Add a named entry under `implementations` in the same file, with a label and blocks. List each part's id in the block of the platform it runs on or lives in: an AI step on the machine whose harness calls the model, a connector with the service it reaches, a person's own step or review on the device they use, and a standing approval where its limits are kept. Label each block with the model and company it uses, any fallback, and when the machine is on, if that isn't always. Nest a block inside another when what runs in it shares that one's access, such as a script the session starts. Where you have a description of a block's platform, name it with `platform`, and run `awml fit --implementation ID workflow.yaml DESC...`. Name one published to the registry as `owner/platforms/slug`, and fetch it first with `awml pull owner/platforms/slug`. Add implementation comments for anything a machine holds that the drawing can't show, such as the keys a step can read, and whether it has a shell or the open web. Each comment names its block with `in` and the parts it explains with `ties`. Run `awml check workflow.yaml` and fix every mistake until it says `ok`. Then draw the security view with `awml draw workflow.yaml`, the untrusted view with `awml draw --untrusted workflow.yaml` if any part is marked untrusted, and the platform view with `awml draw --implementation ID workflow.yaml`.

   For example, a consultant fits a bakery's invoice workflow. The scope allows only named companies, which rules out a host that would keep the invoices. The invoices are local files, which rules out platforms that hold none. The consultant mustn't see them, but their account can drive the container service on the bakery's server, which is as good as full control of it. So the runtime gets its own operating system user, the consultant loses that access, the runtime's credentials get their own OAuth app so grants from the consultant's other clients don't carry across, and the bakery's owner deploys it. The owner keeps that boundary for the invoices, but accepts one held only by instructions for the product list, which the consultant already sees. Both are results of the fit, not failures of it.

10. **Read the drawing for findings.** Ask these of the drawing and the trace:
    1. What does each red line show the live system doing, and which instruction asked for it?
    2. Does every publishing line have a person's yes or a standing rule? Does anything reach the public without a person's yes to that item? Did the people whose words move agree?
    3. Is each yes given to the exact content, and recorded where the next step can check it?
    4. Does any check rely on a mark written by the step it checks, such as a draft that says it was checked?
    5. Does each standing approval cover only actions that can be undone, and does anything outside the agent's instructions keep to its limits?
    6. Is each Allow action really Allow? One that can't be undone, is seen outside its scope or spends past a limit is Ask.
    7. Which step takes in text from strangers, and what can it reach? `awml summary` lists what each untrusted part's text reaches, and `awml draw --untrusted` draws it. Is each `cleans` step's rule sound?
    8. If a step fails halfway, what has already changed outside, and does a later run notice?
    9. Could any AI step be code? Look at a few weeks of its records: does it give the same answer to the same kind of input?
    10. Is any surface, note or prompt left with nothing keeping it current, any context that nothing writes or nothing reads, or any step that nothing starts?
    11. Does any work that must outlive a person rest on that person's connector?
    12. Does any machine hold something that a company processing content there may not see?
    13. Does every step leave a record that survives a restart, on one clock?

11. **Act on each finding.** Take each finding, with its evidence, to the person who answers for the workflow. They decide whether to change the live system. Until it changes, the drawing keeps the finding: a red line for something the live system did, a comment for a gap. When a fix lands, take the red line away.

Then go back to step 3 for the next workflow.
